*Почему стандартный `database/sql` сознательно не стал ORM, как устроен контракт `database/sql/driver` на примере `ledgerdriver`, почему `sql.Open` не проверяет сеть и как безопасно читать строки с учётом `context.Context` и маппинга ошибок.*

> «В идеальном мире прикладному программисту достаточно знать только API — без того, как этот API реализован и к какому железу он обращается. В реальности же чуть более глубокие знания порой оказываются весьма кстати.»  
> — Чарльз Петцольд, *Code: The Hidden Language of Computer Hardware and Software*

При работе с базами данных легко поддаться соблазну спрятать таблицы за толстым слоем объектных обёрток. В PHP (Eloquent), Ruby (ActiveRecord) и Java (Hibernate/JPA) сущности годами маскировали под обычные классы в памяти. Расплата наступала в продакшене: скрытые запросы `N+1`, гигантские кэши первого и второго уровней в куче и непредсказуемые блокировки строк внутри долгих транзакций.

Язык Go возвращает инженера к явной модели. Реляционная СУБД — отдельный сетевой процесс со своими TCP-сокетами, дисковым вводом-выводом и планировщиком транзакций. Стандартный пакет `database/sql` не строит SQL и не генерирует схемы. Он отделяет унифицированный интерфейс доступа и потокобезопасный пул соединений от сетевых протоколов конкретных СУБД.

В карте Модуля 10 этот слой открывает весь раздел: без понимания контракта `database/sql` и `database/sql/driver` любая библиотека поверх него остаётся чёрным ящиком.

## Зачем Go понадобился слой `database/sql/driver`

В разных экосистемах доступ к БД устроен по-разному. В Java спецификация JDBC описывает интерфейс драйверов, но не включает пул — проектам нужен внешний `HikariCP`. В классическом PHP (PDO) процесс умирает после HTTP-запроса, поэтому пул выносят в `PgBouncer` или серверы вроде Swoole и RoadRunner. В Python поверх синхронного DB-API 2.0 (блокирующего поток ОС при наличии GIL) выросли отдельные асинхронные стеки вроде `asyncpg` и пулы `SQLAlchemy`. В C# пул встроен в провайдеры ADO.NET.

Создатели Go выбрали минималистичный путь в духе Bell Labs:
1. Прикладной код работает только с высокоуровневыми типами `database/sql`: `*sql.DB`, `*sql.Tx`, `*sql.Stmt`, `*sql.Rows` и `*sql.Row`.
2. Специфика протокола (PostgreSQL Extended Query, MySQL wire protocol, SCRAM-SHA-256, TLS) вынесена во внешние драйверы, реализующие узкий контракт `database/sql/driver`.
3. `*sql.DB` выступает диспетчером: управляет очередями соединений, мьютексами, отменой через `context.Context` и курсорами, не зная ни байта о формате пакетов СУБД.

## Анатомия драйвера: `sql.Register` против `driver.Connector`

Подключить драйвер к `database/sql` можно через глобальный реестр имён или через интерфейс `driver.Connector`.

Классический способ опирается на побочный эффект (`side-effect import`): при старте `init()` драйвера вызывает `sql.Register("pgx", ...)`. Это удобно в `main.go`, но привязывает приложение к глобальной мапе драйверов и строковому DSN.

Интерфейс `driver.Connector` и функция `sql.OpenDB` (с Go 1.10) позволяют передать драйверу готовую конфигурацию или изолированное состояние без глобального реестра. Именно так устроен автономный драйвер `LedgerPulse` в `project/final/ledgerdriver/driver.go`:

```go
// Фрагмент из project/final/ledgerdriver/driver.go
func (i *Instance) OpenDB() *sql.DB {
	return sql.OpenDB(&connector{inst: i})
}

type connector struct {
	inst *Instance
}

func (c *connector) Connect(_ context.Context) (driver.Conn, error) {
	return &conn{inst: c.inst}, nil
}

func (c *connector) Driver() driver.Driver {
	return Driver{}
}
```

Через `sql.OpenDB(&connector{inst: i})` каждый параллельный тест в `go test` создаёт свой `Instance` поверх настоящего пула `*sql.DB` без конфликта DSN. Одновременно `ledgerdriver` регистрирует имя `"ledgerpulse"` в `init()` через `sql.Register`.

| Интерфейс `database/sql/driver` | Ключевые методы | Роль в диспетчере `*sql.DB` |
|---|---|---|
| `driver.Driver` / `driver.Connector` | `Open(dsn)`, `Connect(ctx)` | Фабрика физических соединений с БД |
| `driver.Conn` | `Prepare`, `Close`, `Begin` | Базовая сессия (старые методы без контекста) |
| `driver.ExecerContext` / `driver.QueryerContext` | `ExecContext`, `QueryContext` | Выполнение SQL с контекстом и параметрами |
| `driver.ConnBeginTx` | `BeginTx(ctx, opts)` | Старт транзакции с `TxOptions` |
| `driver.Pinger` | `Ping(ctx)` | Проверка живости сокета по `db.PingContext(ctx)` |
| `driver.Stmt` / `driver.StmtQueryContext` | `Close`, `ExecContext`, `QueryContext` | Подготовленный запрос на конкретной сессии |
| `driver.Tx` | `Commit`, `Rollback` | Фиксация или откат (в `ledgerdriver` — клон `dbState`) |
| `driver.Rows` | `Columns`, `Close`, `Next(dest)` | Потоковое чтение строк до `io.EOF` |

> [!info] Под капотом: `ledgerdriver` как модель СУБД
> В `project/final/ledgerdriver/driver.go` соединение `conn` хранит `tx *dbState`. На `BeginTx` драйвер клонирует снимок таблиц (`c.inst.state.clone()`), а на `Commit()` под мьютексом делает `c.inst.state = t.c.tx`. При отменённом `ctx` или флаге `failNextBad` метод `runQuery` отдаёт `driver.ErrBadConn` — так же, как живой TCP-сокет при разрыве связи.

## Миф о `sql.Open` и базовая настройка `*sql.DB`

`*sql.DB` — **не одно соединение**, а долгоживущий потокобезопасный менеджер пула. Создавать `*sql.DB` внутри HTTP-хендлера опасно: каждый вызов порождает отдельный пул, быстро исчерпывая файловые дескрипторы процесса (`ulimit -n`) и локальные порты ОС. `*sql.DB` создают один раз при старте сервиса и передают в зависимости.

Вторая частая ошибка — верить, что `sql.Open` проверяет сеть и пароль:

```go
func openLedgerDB(dsn string) (*sql.DB, error) {
	// sql.Open лишь проверяет регистрацию драйвера (иногда формат DSN).
	// Ни один TCP-пакет в сторону СУБД на этом шаге не уходит.
	db, err := sql.Open("pgx", dsn)
	if err != nil {
		return nil, err
	}

	// По умолчанию MaxOpenConns = 0 (без лимита) и MaxIdleConns = 2
	db.SetMaxOpenConns(25)
	db.SetMaxIdleConns(10)
	db.SetConnMaxLifetime(15 * time.Minute)
	db.SetConnMaxIdleTime(5 * time.Minute)

	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel()

	// Физический TCP/TLS handshake и аутентификация идут здесь
	if err := db.PingContext(ctx); err != nil {
		_ = db.Close()
		return nil, err
	}
	return db, nil
}
```

> [!warning] Ловушка: ленивое подключение и дефолты пула
> Без `db.PingContext(ctx)` сервис с выключенной БД запустится без ошибки, пройдёт проверку readiness в Kubernetes и начнёт отдавать клиентам `500`. А не ограниченный `MaxOpenConns = 0` при скачке нагрузки завалит PostgreSQL сотнями процессов, тогда как `MaxIdleConns = 0` заставит закрывать сокет после каждого запроса, переводя тысячи портов в `TIME_WAIT` на 60 секунд.

> [!tip] Собеседование [Junior]
> **Вопрос:** Открывает ли `sql.Open` соединение с базой данных и зачем нужен `db.PingContext`?  
> **Ответ:** `sql.Open` лишь валидирует имя драйвера и инициализирует пул `*sql.DB`. Физическое подключение (TCP, TLS, auth) происходит лениво при первом запросе. `db.PingContext(ctx)` нужен при старте, чтобы сразу проверить доступность БД и права доступа.

Запомните базовое правило пропорций: `MaxIdleConns <= MaxOpenConns` (иначе Go молча урежет `MaxIdleConns`), а `ConnMaxIdleTime` держат короче таймаута простоя NAT/NLB/firewall, чтобы избегать `broken pipe`. Подробно внутреннюю механику пула разберём в следующей главе.

## Жизненный цикл запроса: `QueryRowContext`, `QueryContext`, `ExecContext`

### 1. Одна строка: `QueryRowContext`

Для чтения по ключу или `INSERT ... RETURNING id` (PostgreSQL не поддерживает `LastInsertId` через `Result`) применяют `QueryRowContext`:

```go
var acc Account
err := db.QueryRowContext(ctx,
	`SELECT id, external_id, owner_name, currency, balance, status FROM accounts WHERE id = $1`,
	accountID,
).Scan(&acc.ID, &acc.ExternalID, &acc.OwnerName, &acc.Currency, &acc.Balance, &acc.Status)
if errors.Is(err, sql.ErrNoRows) {
	return Account{}, ErrNotFound
}
if err != nil {
	return Account{}, fmt.Errorf("get account %d: %w", accountID, err)
}
```

Сам `QueryRowContext` ошибку не возвращает: она всплывает в `.Scan(...)`. После `.Scan(...)` структура `*sql.Row` сама закрывает внутренний курсор и возвращает сокет в пул. Но если вызвать `QueryRowContext` и **не вызвать** `.Scan()`, сокет останется занятым до отмены `ctx`.

### 2. Набор строк: `QueryContext`

Для чтения списка записей (как keyset-пагинация в `project/final/repo.go`) вызывают `QueryContext`:

```go
func (r *sqlRepo) ListEntriesKeyset(ctx context.Context, accountID, cursorID int64, limit int) ([]LedgerEntry, error) {
	if limit <= 0 || limit > 200 {
		limit = 50
	}
	rows, err := r.q.QueryContext(ctx,
		`SELECT id, transaction_id, account_id, amount, currency, created_at FROM ledger_entries WHERE account_id = $1 AND id < $2 ORDER BY id DESC LIMIT $3`,
		accountID, cursorID, limit,
	)
	if err != nil {
		return nil, err
	}
	defer rows.Close() // Гарантирует возврат сокета при ошибке, break или панике

	var out []LedgerEntry
	for rows.Next() {
		var e LedgerEntry
		if err := rows.Scan(&e.ID, &e.TransactionID, &e.AccountID, &e.Amount, &e.Currency, &e.CreatedAt); err != nil {
			return nil, err
		}
		out = append(out, e)
	}
	return out, rows.Err() // Ловит сетевой обрыв в середине потока строк
}
```

Три обязательных правила:
1. **`defer rows.Close()` сразу после `if err != nil`:** забытый `Close()` или ранний `break` оставляют соединение в `inUse` навсегда и вешают сервис.
2. **`rows.Err()` после цикла:** `rows.Next()` возвращает `false` и при сетевой ошибке на 50-й строке — без `rows.Err()` сервис отдаст обрезанную выписку.
3. **Ограниченный `limit`:** защита памяти и сокета (см. [[4. ORDER BY, LIMIT и пагинация (OFFSET против keyset)]]).

### 3. Модификация без строк: `ExecContext` и работа с `NULL`

Для `UPDATE`/`DELETE` без `RETURNING` используют `ExecContext`: он возвращает `sql.Result` (`RowsAffected()`) и сразу освобождает сокет. А при сканировании nullable-колонок (`published_at`) обычный `string` или `time.Time` падают с ошибкой драйвера — используйте `sql.NullString`, `sql.NullTime`, `sql.Null[T]` (с Go 1.22), указатели (`*time.Time`) или `COALESCE` (см. [[8. NULL и трёхзначная логика]]).

> [!tip] Собеседование [Middle]
> **Вопрос:** Чем отличаются `QueryContext` и `QueryRowContext` по управлению ресурсами пула?  
> **Ответ:** `QueryContext` отдаёт открытый курсор `*sql.Rows` и требует явного `defer rows.Close()` плюс проверки `rows.Err()`. `QueryRowContext` оборачивает курсор в `*sql.Row` и закрывает его автоматически внутри `.Scan(...)`, но при забытом `.Scan()` сокет зависнет до отмены контекста.

## Отмена по `context.Context`, физика сети и память

Локальное чтение из RAM занимает ~100 нс, страница NVMe — ~100 мкс, а заблокированный запрос к БД способен висеть секундами. Без контекста отключившийся клиент оставит «запрос-зомби» сжигать CPU базы. Поэтому всегда применяют `*Context`-методы.

Контекст работает на двух этапах:
1. Ограничивает ожидание свободного сокета в очереди пула.
2. Запускает наблюдателя за `ctx.Done()`: при таймауте драйвер с `QueryerContext`/`ExecerContext` шлёт серверу сигнал отмены (`CancelRequest` в PostgreSQL) или закрывает сокет.

При этом **отмена `ctx` не возвращает соединение в пул мгновенно**: драйвер ждёт разблокировки системного вызова `read`/`write`, помечает сокет через `driver.ErrBadConn` и закрывает его.

При вызове `rows.Scan(&e.ID, ...)` адреса переменных передаются в другой пакет через `...any`, поэтому анализ побега (*escape analysis*) отправляет буферы и ссылки в кучу. В единичных запросах это теряется на фоне сетевых миллисекунд, а при чтении сотен тысяч строк слайс лучше преаллоцировать (`make([]LedgerEntry, 0, limit)`), переиспользовать структуры или в горячих путях применять нативный интерфейс `pgx` (см. главу 4 этого модуля).

## Маппинг ошибок и чеклист

На границе слоя данных разделяйте три класса сбоев:
1. **Штатное отсутствие строки (`sql.ErrNoRows`)** — преобразуйте в доменную ошибку `ErrNotFound` (`404 Not Found` в `project/final/server.go`), а не в `500`.
2. **Нарушение ограничений схемы** — через `errors.As` проверяйте код драйвера (`*pgconn.PgError`: `"23505"` `unique_violation` → `409 Conflict`, `"23514"` `check_violation` → `422 Unprocessable Entity`; в `ledgerdriver` — `ErrDuplicateKey`, `ErrInsufficientFunds`).
3. **Транзиентные и сетевые ошибки** — `driver.ErrBadConn` (подробно о встроенных повторах `db.retry` в следующей главе) и `context.DeadlineExceeded`.

```go
func mapAccountError(err error) error {
	if err == nil {
		return nil
	}
	if errors.Is(err, sql.ErrNoRows) {
		return ErrNotFound
	}
	var pgErr *pgconn.PgError
	if errors.As(err, &pgErr) {
		switch pgErr.Code {
		case "23505":
			return ErrDuplicateAccount
		case "23514":
			return ErrInsufficientFunds
		}
	}
	return fmt.Errorf("account storage error: %w", err)
}
```

**Чеклист:** один `*sql.DB` на сервис, настроенные `MaxOpenConns`/`MaxIdleConns`/`ConnMaxLifetime`/`ConnMaxIdleTime`, `PingContext` при старте, `*Context` в каждом вызове, `defer rows.Close()` и `rows.Err()`, явный маппинг `ErrNoRows` и SQLSTATE.

### Упражнение 2 (Практическое). Поиск утечки соединения
Найдите две ошибки в функции выписки `LedgerPulse`:
```go
func FetchRecentAmounts(ctx context.Context, db *sql.DB, accountID int64) ([]int64, error) {
	rows, err := db.QueryContext(ctx,
		`SELECT amount FROM ledger_entries WHERE account_id = $1 ORDER BY id DESC LIMIT 50`,
		accountID,
	)
	if err != nil {
		return nil, err
	}
	var amounts []int64
	for rows.Next() {
		var amt int64
		if err := rows.Scan(&amt); err != nil {
			return nil, err
		}
		if amt == 0 {
			break
		}
		amounts = append(amounts, amt)
	}
	return amounts, nil
}
```

> [!solution] Показать решение
> 1. Нет `defer rows.Close()`: при ошибке `Scan` или раннем `break` сокет навсегда остаётся в `inUse`, исчерпывая пул.
> 2. Нет проверки `rows.Err()`: сетевой сбой посреди выборки тихо вернёт неполный слайс.

### Упражнение 3 (Со звёздочкой \*). Счётчик запросов через `driver.Connector`
Как в `LedgerPulse` считать точное число SQL-запросов, доходящих до драйвера, без изменения `LedgerService` и `sqlRepo`? Опишите обёртку над `driver.Connector`.

> [!solution] Показать решение
> Обёртка `MetricsConnector` перехватывает `Connect(ctx)` и возвращает `meteredConn`, который инкрементирует `atomic.Int64` и делегирует вызов `driver.QueryerContext`/`driver.ExecerContext`/`driver.ConnBeginTx`/`driver.Pinger`:
> ```go
> type MetricsConnector struct {
> 	Inner      driver.Connector
> 	QueryCount *atomic.Int64
> }
>
> type meteredConn struct {
> 	driver.Conn
> 	queryCount *atomic.Int64
> }
>
> func (m *MetricsConnector) Connect(ctx context.Context) (driver.Conn, error) {
> 	c, err := m.Inner.Connect(ctx)
> 	if err != nil {
> 		return nil, err
> 	}
> 	return &meteredConn{Conn: c, queryCount: m.QueryCount}, nil
> }
>
> func (m *MetricsConnector) Driver() driver.Driver { return m.Inner.Driver() }
>
> func (c *meteredConn) QueryContext(ctx context.Context, q string, args []driver.NamedValue) (driver.Rows, error) {
> 	c.queryCount.Add(1)
> 	return c.Conn.(driver.QueryerContext).QueryContext(ctx, q, args)
> }
> ```
> Для `sql.OpenDB` это даёт единую точку метрик поверх любого драйвера (важно также пробросить `ExecContext`, `BeginTx` и `Ping`, чтобы `*sql.DB` не откатился на старые методы без контекста).
